## 当前建议

先以有限的来源清单验证采集、证据保存、规范化和人工审查这一条完整流程。
“覆盖所有模型”可以作为长期方向，但它本身不能证明需要通用爬虫平台、分布式队列或常驻数据库。
本项目最先要解决的难点是模型身份、字段含义、来源冲突和条件限制，爬取吞吐量需要实际测量后再判断。

| 环节 | 建议 | 采用条件 |
| --- | --- | --- |
| 核心语言 | Rust stable、Edition 2024 | 承担正式采集核心、规范化、校验、去重和确定性导出 |
| 网络基础 | Tokio + reqwest | 直接访问官方结构化 API、仓库原始文件与静态文档 |
| 数据结构 | Serde + serde_json | 显式反序列化，保留上游原始响应供重放 |
| HTML | scraper | 需要 CSS 选择器提取表格、标题、脚注时使用 |
| 整站爬取 | Spider 候选 | 来源发现确实需要递归跟踪大量链接时评估 |
| 脚本 | Python 3.15 + asyncio + uv | 调研工具、维护命令、少量浏览器适配与批处理 |
| Python HTTP | aiohttp 优先；HTTPX2 候选 | 只在脚本确实需要独立 HTTP 客户端时选择一种 |
| 浏览器 | Playwright Python async API | 页面所需信息不能从公开 API、源码或静态 HTML 取得时使用 |
| YAML 解析 | serde-saphyr、yaml_serde 对比验证 | 先确定受限 YAML 约定，再以相同样例验收 |
| 结构校验 | Rust jsonschema 候选，Draft 2020-12 | schema 起草后，关闭任意网络和文件引用 |
| 权威记录 | YAML + Git | PR 审查、版本比较、来源追踪 |
| 发布产物 | JSON；需要时提供 SQLite | 由同一已审查的 Git 提交生成 |
| 快照 | 本地独立目录起步，之后按需迁往对象存储 | 保存可重放证据；公开范围逐来源判断 |
| 调度 | 手动执行 + 普通 CI 定时任务 | 日级更新、失败可重跑且无需严格准时 |

具体依据与适用边界见两个子报告。
这里的“优先”是结合本项目需求作出的工程判断，不代表整个社区已有唯一共识。

## 2026 年需要特别复核的变化

- Rust YAML 生态不能继续照抄旧选型：`serde_yaml` 已停止维护，`serde_yml` 也已归档；`yaml_serde` 与 `serde-saphyr` 都值得重新评估，详见 [解析器比较](storage.md#rust-yaml-解析器)。
- HTTPX 原项目的稳定发布与维护渠道发生变化，Pydantic 的 HTTPX2 已成为实际候选，详见 [Python HTTP 客户端](collection.md#python-http-客户端)。
- Scrapy 当前已默认启用 asyncio，不能仅用历史上的 Twisted 接入成本否定它，详见 [爬取框架](collection.md#框架与浏览器候选)。
- DuckDB 当前文档已经包含远程多进程写入路线，应区分嵌入模式和远程协议，详见 [查询存储比较](storage.md#查询与分发存储)。

## 下一阶段的最小验证清单

- [ ] 选一个分页 JSON API、一个静态表格页面、一个必须渲染的页面，确认是否真的需要三种适配方式。
- [ ] 在固定样本上测量网络等待、HTML 解析、规范化和校验各自的耗时、峰值内存与失败率。
- [ ] 用相同的异常 YAML 样例比较两个重点解析器候选，确认错误能定位到文件与行列。
- [ ] 用 Python 3.15 建立隔离环境，验证所选库及浏览器驱动；此阶段不预先承诺全部依赖已兼容。
- [ ] 从同一份快照重复运行抽取，确认产出一致、无变化时无 Git diff、失败时不覆盖已审查记录。
- [ ] 验证限流、分页中断、来源结构漂移和临时空结果都不会被误解释为模型删除。

本轮未编写采集器、schema、CI 配置或数据库迁移，也未安装候选依赖。
上游文档可能变化，尤其新发布的解析器与 Python 3.15 兼容性需要在实施时复核。
