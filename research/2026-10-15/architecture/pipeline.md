# 采集、维护与发布流程

[返回架构索引](README.md)

核查日期：2026-10-15。
状态：候选流程，本轮没有创建采集程序、自动任务或发布服务。

## 最小可运行形态

建议从一个可本地运行、可由 CI 调用的批处理工具开始。
按来源组织适配逻辑，给审定数据提供唯一的验证与规范化入口。
Python 只在文档抽取、浏览器或一次性分析明显更方便时承担辅助工作。
Rust 与 Python 通过文件或标准输入输出交换 JSON 数据，先避免语言绑定和驻留服务。

```text
来源登记 → 获取与缓存 → 来源快照 → 提取声明 → 身份映射
                                               ↓
静态导出 ← Git 中的审定 YAML ← 人工审查 ← 校验与差异报告
                                               ↑
                                      冲突与缺失进入待核实队列
```

快照、声明和审定记录是同一批处理过程中的不同状态，可以先落为文件。
无需因为流程存在多步就部署消息队列、微服务或通用工作流平台。

## 每一步需要留下什么

| 阶段 | 输入与输出 | 失败时的行为 |
| --- | --- | --- |
| 来源登记 | URL、来源类型、范围、鉴权方式、分页方式、访问与使用条件 | 条件不清楚则保留调查状态 |
| 获取 | 请求范围、获取时间、状态码、最终 URL、允许保留的响应与摘要 | 超时或限流不会清空现有资料 |
| 提取 | 原始 ID、原始值、证据定位、解析器版本 | 未识别格式进入待处理材料 |
| 映射 | 上游 ID 到本库主体的显式关系 | 不确定映射交给审核 |
| 规范化 | 有单位、有作用域的候选声明 | 不可转换值保留原值并说明 |
| 校验 | 结构、引用、语义、来源新鲜度和冲突结果 | 有问题的批次不覆盖审定数据 |
| 审查 | 小范围 diff、变化原因、证据和已知缺口 | 人工决定收录、延期或否决 |
| 导出 | 指定 Git 提交的确定性 JSON，必要时 SQLite | 导出失败不替换上一份完整产物 |

阶段间不需要一套永久的中间格式规范。
先让首批样本证明哪些内容确实需要保留，再决定目录和接口。

## 获取策略

获取优先级建议为官方结构化 API、官方仓库中的结构化文件、官方静态文档、必要时的浏览器渲染。
聚合目录适合发现候选和补全字段；重要限制回到原始文档核对。
每个适配器声明它的查询范围，尤其是默认模态、分页、账号可见性、地区和版本。
本轮已经发现目录 API 的默认过滤与访问层级会改变「可见模型」集合，详见 [来源目录](../sources/catalog.md)。

按主机限制并发，为请求设超时、响应体上限、最大页数和重试预算。
处理 `Retry-After` 时同时支持日期和秒数。
对支持验证器的来源使用 ETag 或 Last-Modified；收到 304 后更新核查时间，复用已有内容。
HTTP 条件请求和重试字段的语义依据为 [RFC 9110 §13.1.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.2) 与 [§10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)。

一次列表抓取可能跨越上游变更，需保留分页完整性状态和重复 ID 检查结果。
鉴权失败、页面解析失败、分页中断和空结果分别记录，只有完整成功才参与缺失比较。
即使完整结果缺少旧条目，也先复核发布或退役说明，再变更生命周期。

爬取文档时遵循站点访问要求并检查 robots.txt。
robots.txt 规则不等于访问或再分发授权，这一边界在 [RFC 9309 §1](https://www.rfc-editor.org/rfc/rfc9309.html#section-1) 中明确说明。
代码许可证、模型许可证、平台使用条件和目录数据的再分发条件应分别记录。

## 文档抽取与模型辅助

短列表和表格优先确定性解析，保留字段位置或页面章节。
浏览器只用于无法由稳定数据入口获取的页面，并限制导航范围和下载类型。
PDF 或动态网页的表格若无法可靠解析，首批可以人工摘录并保留页码或章节。

大模型可以辅助提出候选声明，但必须附原文定位，并由确定性校验和人工审查确认。
网页、模型卡和候选内容都是数据，不能当作工具执行指令。
让模型生成无证据的字段值会把资料缺口隐藏起来，首批不需要这种自动补全。

## 存储与 diff

Git 中的审定 YAML 是面向维护者的主要数据视图。
输出按稳定 ID 和固定字段顺序生成；有语义顺序的数组保持原顺序。
抓取时间和未变化的运行日志放在获取记录中，避免每次采集制造全库 diff。
数值单位、未知值和枚举先规范化，再比较语义变化。
禁止重复键、任意对象标签和过度复杂的 YAML 结构，具体解析器选择见 [存储研究](../stack/storage.md)。

JSON Schema 负责结构与类型；跨记录 ID 唯一性、引用存在性、关系环路和条件冲突仍需单独的语义检查。
若采用 Draft 2020-12，必须明确 `format` 是否作为断言执行，该草案区分注解与断言词汇。
参见 [JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12)。

## 调度和审查

初期建议手动触发与普通 CI 定时任务，频率按来源变化速度和允许的访问额度调整。
记录每个来源最近一次成功获取、候选变更数量、字段证据覆盖、未决冲突和过期记录数量。
先用一份状态报告满足这些需求，再考虑监控服务。

GitHub 的定时工作流可能延迟，负载过高时任务可能被丢弃，所以不能据此承诺严格更新时间。
参见 [GitHub Actions schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。
抓取任务需要凭据时只运行可信代码；来自外部 PR 的内容验证应在无生产凭据的环境执行。
相关边界参见 [GitHub：Securely using pull_request_target](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)。

具体工具建议见 [采集技术栈](../stack/collection.md)。
只有出现长时间任务、持续跨机器恢复或复杂依赖需求，再评估工作流引擎。

## 最小验证计划

本轮不实现测试；以下是之后编写采集或规范化逻辑时的验收场景。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 相同快照重新运行 | 相同候选与导出内容，运行时间不会改写业务字段 |
| 中途分页失败 | 批次标为不完整，不把剩余模型判为消失 |
| HTTP 304、429、401 与解析失败 | 分别处理，保持最后一份完整审定数据 |
| 同一模型两个平台的上限不同 | 两条服务作用域声明可以并存 |
| 官方正文与示例矛盾 | 证据均保留，结果进入待复核 |
| 滚动别名更换目标 | 旧映射仍可查询，新映射有时间范围 |
| 未知值、重复 YAML 键和悬空引用 | 未知不会变成否定；无效输入不能进入发布物 |
| 抓取页面携带恶意指令或越界链接 | 内容作为数据处理，请求和执行范围不扩大 |
| 生成产物失败 | 已发布完整版本保持可用 |

只有当这些场景有真实输入材料并通过验证，才适合扩大自动采集范围。
