## 建议的数据边界

模型的规格、某个服务的行为、某次观察的结果应能分别定位。
否则同一模型经不同平台提供时，上下文和功能差异容易互相覆盖。
即使完整的服务商目录稍后再做，限制记录也需要从第一版起保留接口作用域。

| 概念 | 回答的问题 | 建议的最小信息 |
| --- | --- | --- |
| 模型家族 | 哪些模型来自同一产品或研究系列 | 稳定 ID、名称、发布组织 |
| 模型版本 | 具体描述哪个发布版本 | 稳定 ID、原始 ID、版本标识、家族、生命周期 |
| 模型变体或产物 | 是否微调、蒸馏、合并、量化或格式转换 | 父版本、关系类型、revision、适用的产物信息 |
| 服务条目 | 哪个平台以什么接口提供它 | 平台、模型参数原值、端点族、API 版本、地区（有影响时） |
| 声明 | 在什么范围和条件下，哪个属性是什么值 | 主体、属性、值、条件、证据引用 |
| 来源与获取记录 | 根据什么、什么时候得出声明 | URL、定位、获取时间、修订或内容摘要、提取方式 |

这些是语义边界，未要求对应六张表、六种文件或六个服务。
首批可以把少量服务限定信息嵌入模型记录，等出现真实复用需求再拆分。

Hugging Face 的模型卡已经支持基础模型、多个父模型和 adapter、merge、quantized、finetune 等关系，并区分新版本链接。
因此跨来源规范化应保留明确的关系类型，不能把所有关联都压成同一个「别名」。
参见 [Hugging Face Model Cards](https://huggingface.co/docs/hub/en/model-cards#specifying-a-base-model)。

## 身份规范化

建议为本库实体分配不随展示名变化的 ID，并保存每个上游的原始 ID 与命名空间。
跨目录映射是一个带证据的关系，不能只靠大小写、标点删除或名称相似度自动合并。

| 情况 | 推荐处理 | 需要避免的误判 |
| --- | --- | --- |
| 同版本在多个托管平台出现 | 模型映射共用，服务信息分别保留 | 平台 ID 等于模型版本 ID |
| `latest` 或无日期的滚动别名 | 单独维护解析关系和观察时间 | 把今天的解析结果用于全部历史 |
| 基础版与 instruct 版 | 关联但保留不同版本身份 | 名称主体一致就合并 |
| 量化、LoRA、微调或合并 | 用关系类型描述，保留发布方 | 推断全部能力和许可证可以继承 |
| 目录删除或返回空列表 | 标记需要复核 | 自动判定模型退役或删除历史 |
| 同名模型来自不同组织 | 命名空间隔离 | 仅用名称作全局主键 |
| 仓库分支更新 | 保留提交或 revision | 把分支名当作不可变版本 |

人工确认过的映射要能被撤销，同时保留旧映射的来源和生效范围。
第一版先做显式映射和待确认候选，模糊匹配只辅助审核。

## 不同模型类型需要不同规格

输入模态、输出模态、任务和接口是不同维度。
「能接收图片」「能生成图片」「能定位物体」「能在 system instruction 中接收图片」分别需要证据。

| 模型任务 | 首批值得调查的元信息 | 单一上下文字段不足的原因 |
| --- | --- | --- |
| 文本生成与推理 | 输入、输出、总预算，推理预算，工具与结构化输出 | 推理与输出可能共享预算，功能受组合条件影响 |
| 图像理解与生成 | MIME、图片数量、尺寸、像素、编辑输入、输出格式 | 限制可能按请求体、图片或分辨率计量 |
| 音频识别、生成与实时交互 | 编码、采样率、语言、时长、流式、说话人能力 | 离线文件和实时会话有不同边界 |
| 视频理解与生成 | 时长、帧率、分辨率、音轨、参考输入 | 时长和媒体参数可能联动 |
| embedding | 输入模态、向量维数、维数可选性、最大批次、截断 | 支持的输入长度不说明向量输出或批量限制 |
| rerank | 查询与文档长度、文档数量、top-n、截断方式 | 多文档总预算和单文档预算不同 |
| 视觉感知、3D、时序或其他专业任务 | 任务、输入结构、输出结构、适用数据、部署形式 | 许多任务没有语言模型式上下文窗口 |

没有发布的训练细节、参数规模或许可证保持未知。
不适用、未公布、尚未调查和明确不支持应能区分；它们不应都变成空字符串或 `false`。

## 条件声明的最小表达

简单且没有争议的属性可以保持平直，例如名称和已确认的发布组织。
涉及接口限制、易变数字或冲突的属性应引用独立证据。
先采用有限的条件词汇，例如接口、版本、角色、输入模态、输出模态和功能组合，不先构建任意表达式语言。
遇到词汇尚不能准确覆盖的条件，保留原文定位和短说明，等待更多真实案例后再结构化。

一条条件声明至少回答以下问题。

1. 主体是模型版本、服务条目还是特定接口？
2. 在哪些条件同时成立时适用？
3. 值是明确支持、明确不支持、有条件支持还是证据不足？
4. 来自官方文档、第三方目录还是可复现的行为观察？
5. 何时获取、何时有效、多久未重新核查？

支持状态和证据类型是两条轴。
`documented` 不等于已经实测，`observed` 也不等于对全部账号、地区、版本成立。
多条声明互相冲突时，保留它们，并在审定视图中标记未解决；不要用看似精确的置信度小数消除冲突。
YAML 讨论示例见 [限制案例](../sources/constraints.md)，避免在多个文件维护不同版本的示例。

## 冲突处理原则

| 冲突 | 处理步骤 | 审定结果 |
| --- | --- | --- |
| 模型页与平台目录上限不同 | 先核对版本、平台、接口、单位和输入输出口径 | 作用域不同则并存 |
| 同一文档正文与代码示例不一致 | 保存两处定位，不从示例外推全族能力 | 待核实，并说明冲突 |
| 官方限制与一次成功请求不同 | 保存请求条件和结果；排除兼容层转换 | 文档声明与观察分别存在 |
| 多个目录一致但引用同一上游 | 记录共同来源 | 不当作多份独立佐证 |
| 最新文档删除旧字段 | 查变更或退役说明 | 删除内容不自动证明属性为否 |

来源优先级应针对属性设置。
发布组织适合由发布方确认，某平台能接收什么适合由该平台的接口文档确认。
官方来源也可能过时或彼此冲突，因此「官方优先」不能替代作用域和时间核对。

## 溯源与时间

W3C PROV-DM 把数据实体、产生数据的活动和负责者区分开。
本项目可以借用这一概念，记录来源页面、提取运行和审核者之间的关系；目前无需引入 RDF 存储或完整本体实现。
这是本项目的简化设计建议，概念依据为 [W3C PROV-DM](https://www.w3.org/TR/prov-dm/)。

| 时间或版本 | 含义 |
| --- | --- |
| 来源发布或修改时间 | 上游自述的时间，可能没有或不可信 |
| 获取时间 | 本次实际读取资料的时间 |
| 最近成功核查时间 | 条件请求或重新提取确认仍有效的时间 |
| 有效区间 | 来源明确说明的适用时期，可未知 |
| 本库提交与发布版本 | 审核结果何时进入可分发视图 |

仅有 Git 历史无法回答一个动态网页在上次提取时究竟写了什么。
建议在允许保存的范围内记录内容摘要、短摘录或结构化响应定位，必要时保存可重放的原始快照。
快照不可公开时，记录访问和保留范围；不能承诺所有证据都能由公众复现。

## 下一阶段需要证实的设计

- 一个真实模型在两个平台的差异能否表达，且模型基本身份不重复？
- system instruction 的限制能否绑定接口，避免误伤普通 user 图片输入？
- 相同属性的矛盾资料是否可同时保存，审核结果是否可解释？
- 未知、明确不支持和不适用是否会被导出逻辑误合并？
- 修改一条限制时，审查者能否在一个小 diff 中看到值、条件和证据变化？
- 同一快照重新提取是否得到相同记录，旧别名映射是否仍可追溯？

这些问题通过后再冻结第一版 schema。
